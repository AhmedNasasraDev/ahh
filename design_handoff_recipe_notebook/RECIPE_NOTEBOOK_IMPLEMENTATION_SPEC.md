## 3. Progressive Disclosure ופרופילים

שלושה פרופילים, נבחרים ב־onboarding וניתנים לשינוי בהגדרות:

| פרופיל | ברירת יחידות | `pro` | מה נחשף קודם |
|---|---|---|---|
| ביתי | g, cup, tbsp, tsp, unit | false | מתכון, Cook Mode, המרות. בלי עלויות ותשואה |
| מקצועי | g, kg, ml, l, unit | true | הכול: תשואה, פחת, עלות, נוסחה, יום ייצור |
| לימוד | g, ml, cup, unit | true | מצב לימוד וקבוצות מקדימים; נתוני ייצור זמינים |

**חוק מחייב:** הפרופיל קובע ברירות מחדל ורמת חשיפה ראשונית בלבד. **הוא אינו נועל שום פיצ'ר.** כל כלי מקצועי נגיש בכל פרופיל דרך "נתוני ייצור ועלויות" או תפריט "עוד".

מתג `pro`/`simple` שולט על: בלוקי תשואה־פחת־עלות במסך המתכון, עמודות מחיר במסך מלאי, ותצוגת מחירים בשיתוף.

החלפת פרופיל דורסת את `units` **רק אם** `touchedUnits === false`.

## 4. Onboarding

שלושה צעדים, מופיע פעם אחת (`prefs.done === false`), עם "איפוס והרצת שאלות הפתיחה מחדש" בהגדרות.

1. **"איך נוח לכם לעבוד?"** — שלושה כרטיסי פרופיל.
2. **"איך נוח לכם למדוד במתכונים?"** — בחירה מרובה, מחולקת לקבוצות: משקל (mg, g, kg, oz) · נפח (ml, l, fl oz) · מדידות ביתיות (כוס, כף, כפית) · יחידות (יחידה, ביצה, פרי, פרוסה) · בר וקפה (shot). הערה קבועה: *oz הוא משקל, fl oz הוא נפח, והם לא מומרים זה לזה בלי לדעת מה חומר הגלם.*
3. **"מה גודל כלי המדידה שלכם?"** — כוס (240 / 250 / 8 fl oz / 9 fl oz / 10 fl oz), כף (15 / 14.8 / 20), כפית (5 / 4.93).

**Validation:** אפשר להמשיך גם בלי בחירה — ברירת המחדל של הפרופיל נכנסת לתוקף. סיום קובע `prefs.done = true`.

**States:** `onbStep` 0–2 · נקודות התקדמות · "הקודם" מוצג רק מצעד 2.

## 5. המרת יחידות — הליבה החישובית

מיושם ב־`measure.js`. **חוק מוחלט: אין חוק המרה כללי מנפח למשקל.** כל המרה כזו תלויה בחומר הגלם.

### 5.1 סדר קדימות של מקור הצפיפות

`densityFor(ingredient, prefs, unit)` מחזיר `{ per100, source, note }` או `null`:

1. `personal` — כיול אישי של המשתמש לחומר הגלם הזה. ירוק, מסומן "מדויק".
2. `recipe` — `ingredient.gPer100` שהוזן במתכון עצמו. ירוק.
3. `system` — טבלת צפיפויות (`TABLE`, 25+ חומרי גלם: קמח 50 גר'/100 מ"ל, סוכר 83, אבקת סוכר 46, קורנפלור 48, חמאה 95, דבש 142…). ענבר, "נתון מערכת".
4. `estimate` — נתון שמשתנה מאוד לפי חומר הגלם עצמו (למשל קפה טחון, תלוי בדרגת הטחינה). אדום, "הערכה גסה".
5. **אין נתון → `null`. אסור להציג מספר.** במקומו: *"אין נתון אמין להמרת X בין נפח למשקל. אפשר לשקול כוס אחת ולהוסיף כיול אישי."*

### 5.2 סוגי המרה

| מ־ | אל | שיטה | דיוק |
|---|---|---|---|
| משקל | משקל | יחס קבוע | מדויק |
| נפח | נפח | יחס קבוע לפי גודל הכלי | מדויק |
| נפח | משקל | דרך `densityFor` | לפי המקור |
| משקל | נפח | דרך `densityFor` | לפי המקור |
| ספירה | משקל | `ingredient.unitWeight`, ואם אין — משקל יחידה ממוצע | מדויק / הערכה |
| ספירה | נפח | ספירה → משקל → נפח | הערכה |

`fmt()` מעגל לכלי המדידה: רבעי כוס, חצאי כף/כפית.

### 5.3 UI — גלית "המר יחידה"

נפתחת בלחיצה על **כל שורת רכיב** במסך המתכון. מציגה:

- הכמות והיחידה **כפי שכתוב במתכון**
- הכמות המוצגת כרגע (אחרי סקיילינג)
- **גודל כלי המדידה** לפי ההגדרות של המשתמש
- יחידות יעד לבחירה
- התוצאה
- **תג מקור**: כיול אישי / נתון מהמתכון / המרה מדויקת / נתון מערכת / הערכה גסה — כולל צבע וההסבר למה
- כפתור "לכייל את הרכיב הזה אצלי במטבח" → מעביר למסך כלי המדידה עם השם ממולא

**Edge cases:** רכיב שהוא תת־מתכון — אין המרה, נמדד בגרם. כמות 0 — "אין כמות להמיר". יחידה לא מזוהה — "יחידה לא מזוהה".

### 5.4 המרת מתכון שלם

שלושה מצבי תצוגה במסך המתכון: **כמו במתכון · גרמים · ביתי**.

- המצב משנה **תצוגה בלבד**. `state.view` אינו נשמר על המתכון.
- רכיב שאין לו נתון אמין נשאר בגרמים ומקבל הערה "נשקל בגרם, אין נתון אמין".
- בתצוגה לא־מקורית מופיעה שורה: *"התצוגה הזאת אינה שומרת דבר. אפשר לשמור אותה כגרסה נפרדת במחברת."* + "שמירה כגרסה" → יוצר מתכון חדש עם `versionOf` והיחידות המומרות.

## 6. שינוי מנות ותפוקה

ארבעה מצבי סקיילינג במסך המתכון: **כמו במתכון · יחידות · משקל · לפי מלאי**.

- יחידות: יעד יחידות → מקדם.
- משקל: משקל סופי רצוי → מקדם.
- לפי מלאי: "יש לי 4 ק"ג קמח" → מקדם נגזר מהרכיב הנבחר.
- **המתכון המקורי לעולם אינו נדרס.** המקדם חי ב־state, וכל המסך מחושב מחדש.
- אזהרה כאשר היחידות בפועל חורגות מ־5% מהיעד.

**חסר ומיועד להוספה:** מצב "נפח סופי" (ליטרים) — רלוונטי לברמנים ובריסטות. החישוב קיים (`mlPerUnit`), נדרש רק מצב סקיילינג נוסף.

## 7. תבניות וציוד

`PAN_KINDS`: עגולה (Ø, גובה) · מלבנית (רוחב, אורך, גובה) · GN (1/1, 1/2, 1/3, 2/3, 1/6) · אינגליש קייק · מאפינס (מספר שקעים) · בלי תבנית.

`panFactor(from, to)`:
- שני הגבהים ידועים → יחס **נפח**: `(area_to × h_to) / (area_from × h_from)`
- אחרת → יחס **שטח**: `area_to / area_from`

**UI:** במסך מתכון שיש לו `pan`, כרטיס "תבנית" מציג את תבנית המתכון, בורר "התבנית שלי", והצעה: *"התבנית שלכם גדולה פי 1.69 בשטח. מומלץ להכפיל את כל הכמויות במקדם הזה."* + "התאמה". ההתאמה קובעת מצב סקיילינג משקל — כלומר **חישוב, לא דריסה**.

סף: הצעה מוצגת רק כאשר `|factor − 1| > 0.02`.

## 8. הערות אישיות

- שדה `privateNotes` על המתכון האישי — נפרד לגמרי מ־`notes`.
- **אינו נכנס** לדף ההזמנה, לתווית, לשיתוף או לייצוא קבוצתי.
- על מתכון **קבוצתי** ההערה נשמרת ב־`myNotes["<groupId>:<itemId>"]` ולא נוגעת במתכון המקור.
- שמירה עם debounce של 400ms.
- `REQUIRES BACKEND`: אחסון פר משתמש עם RLS שמונע כל קריאה זרה, כולל של המדריך.

## 9. גרסאות מתכון

- כל שמירה של מתכון קיים דוחפת `Version` עם `tag`, תאריך, **תיאור מה השתנה** (`versionDiff`) ו־`snapshot` מלא.
- `versionDiff` מזהה: שינוי שם, רכיב שנוסף, רכיב שהוסר, שינוי כמות (עד 3 שמות), שינוי מספר שלבים, ושינוי תשואה מחושבת. אם דבר לא זוהה — "שינויים קלים".
- UI: ציר גרסאות במסך המתכון, `V1…Vn` + "נוכחית", וכפתור **שחזור** לכל גרסה. שחזור אינו מוחק — הוא דוחף את הגרסה הנוכחית להיסטוריה ואז מחזיר את ה־snapshot.
- מתכון `locked` — אין שחזור עד ביטול הנעילה.
- מסך `diff` מאפשר השוואה בין שני מתכונים שונים (לא רק גרסאות).

**קבוצה פרטית כברירת מחדל.** אינה מופיעה בחיפוש ואי אפשר להיכנס אליה מעצמך. ארבע דרכי הצטרפות: הזמנה אישית (מייל/טלפון) · קישור פרטי (חד־פעמי, תוקף 7 ימים) · קוד קבוצה (+ אישור מנהל) · אישור מנהל לבקשה.

### 10.3 מבנה

`Group → Course → Lesson → GroupRecipeItem`. כל `Lesson` נושא תאריך, סיכום וסטטוס. כל `GroupRecipeItem` מפנה ל־`recipeId` ונושא אובייקט `perms`.

### 10.4 הרשאות פר־מתכון

ברירת המחדל היא **המגבילה ביותר**: `{ view: true, save: false, print: false, download: false, shareOut: false }`.

| מפתח | משמעות |
|---|---|
| `view` | בלי צפייה המתכון לא מופיע לתלמיד כלל |
| `save` | שמירת עותק אישי למחברת |
| `print` | הדפסה |
| `download` | הורדת קובץ |
| `shareOut` | שיתוף מחוץ לקבוצה |

**UI:** מסך "הרשאות" למי שיש לו `perms` — כל מתכון בקבוצה, חמישה מתגים מותר/חסום. במסך המתכון הקבוצתי התלמיד רואה כרטיס "מה מותר לי כאן" עם ✓/— לכל הרשאה.

## 11. שמירת מתכון מהקבוצה למחברת

תנאי: `perms.save === true`.

בלחיצה על "שמירת עותק למחברת שלי":
1. אם קיים כבר מתכון עם `savedFrom === "<groupId>:<itemId>"` — לא נוצר כפל; המשתמש מנווט לעותק הקיים עם הודעה.
2. אחרת נוצר עותק: `id` חדש, שם + "— העותק שלי", `locked: false`, `savedFrom` מוגדר, `versions`/`trials`/`batches` מאופסים, ההערה האישית מהקבוצה מועברת ל־`privateNotes`, `versionNote` = "עותק אישי מהקבוצה X".
3. ניווט למתכון האישי + הודעה: *"נוצר עותק אישי במחברת שלכם. המתכון של הקבוצה לא השתנה."*

העותק ניתן לעריכה, לשינוי כמויות, להמרות ולניסויים. **מתכון המקור של הקבוצה אינו משתנה לעולם.** אם המדריך מעדכן את המקור, העותק לא מתעדכן (נדרשת החלטה עתידית: התראה "יש גרסה חדשה בקבוצה").

`perms.save === false` → הכפתור מוחלף בהודעה: *"המדריך לא אישר שמירה של המתכון הזה למחברת אישית. אפשר לצפות ולכתוב הערה אישית."*

## 12. מודל פרטיות — חוקים מחייבים

1. המחברת האישית **פרטית כברירת מחדל**.
2. תלמיד אינו רואה מחברות של תלמידים אחרים.
3. **מדריך ומנהל אינם רואים את המחברת האישית של התלמיד** — לא את המתכונים, לא את ההערות, לא את הכיול האישי, לא את הניסויים.
4. שיתוף קורה **רק** ביוזמת המשתמש.
5. כיול אישי והעדפות מדידה שייכים לחשבון ולא נשלחים לקבוצה.
6. הרשאות `shareOut` שולטות בהוצאת מתכון קבוצתי מחוץ לקבוצה.

הממשק משקף את המודל הזה במפורש, גם בשלב ה־Mock: כל מסך שנוגע בפרטיות נושא הסבר קצר במקום שבו הפעולה קורית, ולא בעמוד תנאים נפרד.

## 13a. מעקב אצוות ו־HACCP

מסך `batch`. נוסף על מעקב האצוות שהיה קיים (מספר אצווה, תאריך, טמפ' ליבה, טמפ' קירור, משקל, אחראי).

### נקודות בקרה (CCP)

ארבע נקודות בקרה קבועות, מוגדרות ב־`Component.CCPS`:

| id | נקודת בקרה | גבול קריטי |
|---|---|---|
| `core` | טמפ' ליבה נמדדה ותועדה | מעל 75°C באפייה, או לפי נוהל המוצר |
| `chill` | קירור מהיר הושלם | מתחת ל־5°C בתוך 4 שעות מסוף האפייה |
| `clean` | משטחים וכלים נוקו לפני העבודה | לפי נוהל הניקיון של המטבח |
| `alrg` | הפרדת אלרגנים נשמרה | כלים נפרדים או ניקוי מלא בין מוצרים |

הרשימה קבועה בשלב ה־Design. **REQUIRES BACKEND:** נקודות בקרה פר־מטבח או פר־מוצר, כולל עריכה של הגבולות הקריטיים, דורשות טבלה משלהן.

### חישוב הסטטוס — `haccpOf(batch)`

לוגיקה דטרמיניסטית, ארבעה מצבים, בסדר בדיקה זה:

1. כל ארבע ה־CCP מסומנות **וגם** `chillTemp <= 5` → **"HACCP תקין"** (ירוק `#E2EFE8`/`#1E6B4C`)
2. `chillTemp > 5` → **"חריגה"** (אדום `#F6E3E0`/`#9E362C`) — קודם לכל סימון, כי זו מדידה ולא הצהרה
3. אפס CCP מסומנות → **"לא תועד"** (אפור `#EDEFEC`/`#6E7A73`)
4. אחרת → **"חלקי"** (ענבר `#F6EBD6`/`#A56A0E`)

הסטטוס נשמר נגזר ולא מאוחסן — הוא מחושב מחדש מ־`ccp` ומ־`chillTemp` בכל רינדור. אין דרך לסמן אצווה כתקינה בלי התיעוד שמאחוריה.

### תיעוד מצולם

`<image-slot id="batch-photo">` בכרטיס האצווה החדשה. בשמירה נרשם `photo: boolean` על האצווה, והרשימה מציגה "עם צילום".

**REQUIRES BACKEND:** הצילום עצמו נשמר כרגע במכשיר בלבד דרך ה־image-slot. נדרש: העלאה ל־bucket פרטי, `batch_photos(batch_id, storage_path, taken_at, taken_by)`, ריבוי צילומים לאצווה, וחתימת זמן שאינה ניתנת לעריכה על ידי המשתמש — בביקורת מזון חותמת זמן שהמשתמש יכול לשנות אינה שווה דבר.

### קישור לתווית המוצר

מסך `label` מציג את סטטוס ה־HACCP של **האצווה האחרונה** לצד מספר האצווה:

- סטטוס תקין → "כל נקודות הבקרה תועדו לאצווה הזאת"
- כל סטטוס אחר → "לפני הדפסה יש להשלים את התיעוד במעקב האצווה"

זו הודעה מיידעת ולא חסימה. **החלטת UX:** אנחנו לא חוסמים הדפסת תווית על סטטוס חסר, כי במטבח אמיתי חסימה כזאת מייצרת דריסה ולא תיעוד. **REQUIRES BACKEND:** אם הלקוח דורש אכיפה, היא צריכה להיות מוגדרת פר־מטבח ונאכפת בשרת בעת יצירת התווית, לא בדפדפן.

### Edge cases

- אין אצוות למתכון → לא מוצג שום סטטוס על התווית, לא "לא תועד".
- אצווה נמחקת והיא הייתה האחרונה → התווית חוזרת לאצווה שלפניה, או לשום סטטוס.
- `chillTemp` ריק → אינו נחשב חריגה. שדה ריק אינו מדידה.
- אצוות שנרשמו לפני הפיצ'ר → `ccp` חסר, נקרא כאפס סימונים, מוצג "לא תועד".

### Acceptance

1. אצווה עם ארבע CCP וקירור 4°C מציגה "HACCP תקין", והתווית מאשרת זאת.
2. אותה אצווה עם קירור 7°C מציגה "חריגה" גם כשכל ה־CCP מסומנות.
3. מחיקת האצווה האחרונה מעדכנת את התווית מיד.
4. אצווה מלפני הפיצ'ר אינה שוברת את המסך ואינה מוצגת כתקינה.

## 18. Edge Cases

1. אין נתון צפיפות → **לא מציגים מספר**, מציעים כיול.
2. `oz` מול `fl oz` — לעולם לא מומרים זה לזה ישירות; רק דרך צפיפות חומר הגלם.

4. כיול של כוס נגזר לכף ולכפית ביחס נפח, ומסומן "נגזר מהכיול של כוס".

6. תת־מתכון — אין המרת יחידות, נמדד בגרם.
7. מתכון `locked` — עריכה דורשת אישור, שחזור גרסה חסום.
8. שמירת עותק פעמיים מאותו מתכון קבוצתי — לא נוצר כפל.
9. מתכון קבוצתי בלי `view` — לא מופיע כלל ברשימת השיעור.
10. תבנית בלי גובה → התאמה לפי שטח בלבד, והמשתמש מקבל לדעת זאת.
11. פחת אפייה מחושב ממדגם; בלי מדגם — 0 ולא ניחוש.
12. יחידות בפועל חורגות מהיעד ב־>5% → אזהרה אדומה.

16. כל מסך תקין ב־RTL, ומספרים ומחירים מיושרים LTR בתוך הקשר RTL.
17. אין שום מסך שבו פעולת Mock מוצגת כאילו היא מחוברת לשרת.

# CLAUDE CODE HANDOFF

## מה קיים ומה נדרש

ה־Design הוא אפליקציית דפדפן עובדת עם מנוע חישוב אמיתי. **אין לשכתב את המנוע.** `engine.js` ו־`measure.js` הם הנכס המרכזי של המוצר ויש להעביר אותם כמעט as-is לשכבת הלוגיקה (או לשתף אותם בין client ו־server כמודול משותף).

מה שנדרש הוא להחליף את שכבת האחסון והזהות: מ־`window.storage` עם מפתח אחד, למסד נתונים עם חשבונות, קבוצות ו־RLS.

## 2. Auth

- Email/password או OTP. שום מסך אינו מניח provider מסוים.
- ה־onboarding רץ אחרי ההרשמה הראשונה וכותב ל־`profiles`.
- `prefs` נטען עם הסשן ומשפיע על כל ההמרות בכל המכשירים.

## 3. RLS — קריטי

```
recipes:            SELECT/UPDATE/DELETE WHERE owner_id = auth.uid()
                    OR (group_id IS NOT NULL AND user is member AND perm_view)
private_notes:      ALL WHERE user_id = auth.uid()          -- ללא יוצא מן הכלל
calibrations:       ALL WHERE user_id = auth.uid()
profiles:           ALL WHERE user_id = auth.uid()
trials/batches:     דרך recipe → owner_id = auth.uid()
group_members:      SELECT WHERE user is member of that group
group_recipe_items: SELECT WHERE user is member AND perm_view
                    UPDATE WHERE user role IN ('owner','instructor')
groups:             SELECT WHERE user is member         -- אין גלישה ציבורית
courses/lessons:    SELECT WHERE user is member
```

**חוק שאין לעבור עליו:** אין שום policy, view, RPC או דוח שמאפשר ל־`owner`/`instructor` לקרוא `recipes` של תלמיד (`group_id IS NULL`) או `private_notes` של מישהו אחר. זו דרישת מוצר, לא הקשחה אופציונלית.

## 4. Endpoints / RPC נדרשים

```
POST /groups/:id/invite        { email }        → יוצר invite + שולח מייל
POST /groups/join-by-code      { code }         → יוצר בקשה ממתינה
POST /groups/join-by-token     { token }        → חבר, אם התוקן בתוקף ולא נוצל
POST /groups/:id/approve       { userId }       → owner/instructor בלבד
PATCH /group-items/:id/perms   { perm_* }       → owner/instructor בלבד
POST /group-items/:id/save-copy                 → מבצע §11 בצד שרת:
       בודק perm_save, בודק saved_from קיים, יוצר עותק מלא בבעלות המשתמש
POST /recipes/:id/versions                      → דוחף גרסה עם snapshot + diff
POST /recipes/:id/restore/:versionId
POST /convert                  { ingredient, toUnit }  → אופציונלי; אפשר גם client-side
PATCH /ingredient-catalog/:id  { price }        → מתפשט לכל המתכונים של המשתמש
POST /paste/parse              { text }         → proxy ל־Claude API. המפתח לא בדפדפן
```

**`save-copy` חייב להיות בצד שרת.** בדיקת `perm_save` בצד לקוח היא UX בלבד.

## 5. Storage

- תמונות מתכון, תמונות קטגוריה, תמונות אצווה (§13a — כולל חותמת זמן שאינה ניתנת לעריכה).
- Bucket פרטי, גישה חתומה. תמונה של מתכון אישי אינה נגישה לקבוצה.
- מגבלת גודל והמרה ל־WebP בהעלאה.

## 6. Security

- ה־Claude API key מעולם לא בדפדפן — proxy בלבד, עם rate limit פר משתמש.
- טוקני הזמנה: חד־פעמיים, תוקף 7 ימים, נבדקים בצד שרת.
- קוד קבוצה אינו מעניק חברות — הוא יוצר **בקשה** שדורשת אישור.
- כל בדיקת הרשאה שהמשתמש רואה ב־UI חייבת להיאכף שוב בשרת.
- מחיקת חשבון מוחקת `private_notes` ו־`calibrations` מיד.

## 7. סדר עבודה מוצע

1. Auth + `profiles` + זריעת `density_table`. ה־onboarding מתחבר למסד.
2. `recipes`/`ingredients`/`steps` + RLS אישי. המחברת עובדת מול DB.
3. `recipe_versions` + restore.
4. `private_notes` + `calibrations` — הראשונים לבדיקת RLS.
5. `groups`/`courses`/`lessons`/`group_recipe_items` + קריאה לפי חברות.
6. הרשאות + `save-copy` בצד שרת.
7. הזמנות, קוד, אישורים.
8. Storage לתמונות.
9. Proxy לפענוח חכם.
10. `batch_photos` + חותמת זמן מאומתת שרת (§13a).
11. Locale ערבית.

## 8. מה לא לעשות

- לא לשכתב את `engine.js` או `measure.js`.
- לא להמציא נתוני צפיפות שאינם בטבלה. `null` הוא תשובה לגיטימית ומוצגת כראוי.
- לא להמיר `oz` ל־`fl oz` ישירות.
- לא לתת למדריך גישה למחברת האישית או להערות של תלמיד, בשום דוח.
- לא לדרוס מתכון מקורי בעת חישוב, סקיילינג, המרה או התאמת תבנית.
- לא לאפשר סימון אצווה כתקינת HACCP בלי התיעוד שמאחוריה, ולא לתת למשתמש לערוך חותמת זמן של צילום.
- לא לנעול פיצ'ר מקצועי מאחורי פרופיל. הפרופיל קובע חשיפה ראשונית בלבד.
- לא לשנות את השפה העיצובית (§16) בלי סיבה מקצועית מוצדקת.
